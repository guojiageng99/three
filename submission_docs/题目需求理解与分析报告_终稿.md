# 题目需求理解与分析报告

## 题目信息

**项目名称：** Generative Agents 论文复刻  
**论文名称：** *Generative Agents: Interactive Simulacra of Human Behavior*  
**项目定位：** 课程作业演示型最小完整机制复刻  
**交付形式：** 代码、PPT、分析报告、方案报告、讲解视频

## 摘要

本文围绕论文 *Generative Agents: Interactive Simulacra of Human Behavior* 展开需求理解与分析。论文的核心目标是让多个生成式智能体在开放环境中持续感知、记忆、规划、行动与社交互动，从而形成近似真实社会的行为演化过程。考虑到课程作业的时间约束与展示要求，本项目将论文中的大规模社会仿真问题压缩为一个 Smallville 风格的小镇 demo，重点复刻“感知、记忆检索、计划、行动/对话、记忆更新、反思”这一最核心闭环。本文从题目背景、需求拆解、核心场景、关键问题、范围控制、验收标准等角度进行系统分析，明确本项目的本质不是论文级全量复现，而是在有限时间内完成一个可运行、可解释、可演示、可交付的最小完整机制系统。

## 关键词

Generative Agents；多智能体；记忆检索；反思机制；课程作业复刻；Smallville

## 一、题目背景与研究意义

随着大语言模型的发展，智能体系统的研究正在从“单轮问答”逐渐走向“长期行为生成”。传统脚本式 NPC 往往只能执行预先设定的动作序列，缺乏持续记忆、情境适应和社会互动能力。相比之下，生成式智能体强调：

1. 智能体应具备跨时间延续的状态。
2. 当前行为应受过往记忆和当前环境共同驱动。
3. 多个智能体之间应形成信息传播和社会关系演化。
4. 高层反思应能反馈到后续计划和行为中。

论文 *Generative Agents* 正是在这样的背景下提出。其价值不仅在于展示一个“会走动的虚拟小镇”，更在于探索如何通过大语言模型将角色行为组织成具备一致性、连续性与社会性的过程。

对于课程作业而言，复刻这篇论文具有明显意义：

- 可以体现对大模型驱动智能体系统的理解。
- 可以展示“论文机制到工程实现”的转化能力。
- 可以形成视觉上清晰、便于答辩的视频与演示材料。

## 二、题目需求理解

### 2.1 题目的本质

本题的本质不是“做一个漂亮的前端页面”，也不是“写一个简单 NPC 移动脚本”，而是：

`构建一个具备最低限度认知闭环的生成式智能体演示系统。`

其中所谓“最低限度认知闭环”至少应包括：

- 环境感知
- 记忆记录
- 记忆检索
- 计划驱动
- 行动或对话生成
- 高层反思

### 2.2 课程作业场景下的真实要求

结合提交模板和最终交付要求，可以将本题理解为一个“技术复刻 + 课程演示”双目标问题。  
也就是说，项目既要有真实的机制支撑，也要有足够明确的可展示效果。

因此最终系统必须同时满足：

- `可运行`：代码能够启动并完成 demo 演示。
- `可解释`：能说明智能体为什么这样行动。
- `可展示`：界面足够清晰，适合录视频。
- `可成文`：架构、模块、数据流与取舍能够写进报告。

## 三、需求拆解

### 3.1 功能性需求

系统需要满足以下功能性需求：

1. 提供一个固定的小镇环境，包含多个地点。
2. 提供多个具有差异化 profile 的 NPC。
3. 支持时间推进与角色移动。
4. 支持日计划驱动的行为调度。
5. 支持事件记忆记录与存储。
6. 支持根据情境检索相关记忆。
7. 支持角色之间的对话与信息传播。
8. 支持高层 reflection 生成。
9. 提供前端解释面板展示当前状态。

### 3.2 非功能性需求

除功能需求外，本项目还存在较强的非功能性要求：

- 演示稳定性要高，不能严重依赖网络状态。
- 系统逻辑要足够直观，便于讲解。
- 项目结构要清晰，便于短时间内完成报告与 PPT。
- 复杂度必须受控，避免在交付前失控。

### 3.3 交付性需求

从课程提交角度，还必须满足：

- 提供完整代码
- 提供 PPT
- 提供需求分析报告
- 提供技术方案报告
- 提供讲解视频

因此项目不能只关注代码实现，还必须同时兼顾文档和演示素材沉淀。

## 四、核心场景分析

### 4.1 环境场景

本项目选择 Smallville 风格小镇作为演示环境，原因在于：

- 结构清晰，适合地图展示
- 地点有限，便于控制复杂度
- 容易设计相遇、传播和对话场景

当前系统中包含的典型地点有：

- Alice's Home
- Johnson Park
- Hobbs Cafe
- Town Square

### 4.2 社交传播场景

为了让系统更像论文中的社会性环境，而不是单个角色的行为模拟，本项目选择了“信息传播链”作为核心剧情：

- Alice 最初知道 evening gathering
- Alice 在 cafe 将信息告诉 Bob
- Bob 在 square 将信息告诉 Carol
- 多个角色掌握信息后形成 shared reflection

这一场景具备三重价值：

1. 便于展示角色对话
2. 便于展示记忆如何跨角色传播
3. 便于展示 reflection 的形成条件

### 4.3 可解释行为场景

课堂答辩时，老师通常不仅关注“系统有没有动”，还会问：

`为什么这个角色现在会做这件事？`

因此本项目需要专门提供：

- 当前 active plan
- 当前检索到的记忆
- 当前 utterance
- 当前 reasoning context

这使得行为结果和其依据能够一一对应。

## 五、关键问题分析

### 5.1 如何避免做成纯脚本系统

如果角色行为完全由固定剧情驱动，那么系统虽然“能演示”，但并不能体现 generative agents 的核心思想。  
因此必须保证：

- 当前动作依赖于当前情境
- 当前动作依赖于检索出的记忆
- 当前系统存在 reflection 层

### 5.2 如何控制工程规模

论文原始系统具有更大规模的人物和更长周期的社会演化，这在课程作业中成本过高。  
因此必须主动收缩范围：

- 角色数降低到 3 个
- 地点数降低到 4 个
- 检索机制采用轻量规则打分
- 演示链设计为一条稳定可控的信息传播线

### 5.3 如何兼顾“像大模型系统”和“能稳定演示”

如果所有行为都完全依赖外部 API，则演示容易受网络影响。  
如果完全不调用模型，则缺少课程中的大模型特色。  
因此最合理的需求解读是：

- 支持大模型接口
- 允许无 key 时 fallback 稳定运行

## 六、项目范围界定

### 6.1 纳入范围

本项目纳入范围的内容包括：

- 小镇地图可视化
- 3 个 NPC
- 时间推进
- 计划驱动移动
- 记忆记录与检索
- 对话传播
- reflection 生成
- reasoning context 展示

### 6.2 不纳入范围

本项目不纳入范围的内容包括：

- 论文级大规模 NPC 数量
- 多天长期仿真
- 多模态输入
- 强化学习
- 复杂向量数据库
- 论文原始实验指标的严格复现

### 6.3 范围控制的必要性

这一范围划分并不是“做少了”，而是为了在课程作业时限内把最关键的机制做扎实。  
从交付角度看，这样的取舍比盲目扩功能更合理。

## 八、验收标准分析

从课程作业展示的视角，项目是否完成可以用以下标准判断：

1. 系统能正常启动并展示地图与多个 NPC。
2. NPC 能按计划随时间推进而变化位置与动作。
3. 系统能展示当前记忆、检索结果和 reasoning context。
4. 至少有一条完整的信息传播链。
5. 能形成 reflection。
6. 能支撑 PPT、报告和视频讲解。

只要满足以上条件，项目就已经具备较强的课程交付能力。

## 九、结论

通过需求分析可以看出，本项目本质上是一个“受时间限制的论文机制压缩复现问题”。  
其成功标准不是是否达到论文级复杂度，而是能否在有限时间内构建一个：

- 可运行
- 可解释
- 可演示
- 可成文
- 可交付

的最小完整机制系统。

因此，本项目当前采用的路线是合理且必要的：  
`优先复刻核心闭环，再围绕交付要求组织代码、PPT、报告与视频材料。`
